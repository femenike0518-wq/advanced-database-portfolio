# SwiftBank Distributed Database Architecture

## Proposed design
SwiftBank uses PostgreSQL as its authoritative relational database. Account updates and money movement are written to the primary. A standby can receive WAL changes and support read-only access or recovery planning, subject to replication lag and a tested failover process.

## Practical implementation
I configured a separate local PostgreSQL 18.6 physical standby using `pg_basebackup`. The existing server remained the primary on port 5432; the standby used a separate data directory and port 5433. The primary reported the standby as `streaming` with asynchronous replication. A marker written to an isolated `p5_replication_demo` table appeared on the standby, and PostgreSQL rejected a standby write with SQLSTATE `25006`. This verifies local streaming and read-only behavior. I did not promote the standby or test failover.

## Design considerations
Asynchronous replication can leave recent changes unavailable on a standby during lag or a primary failure. SwiftBank should keep balance-changing transactions on the primary and monitor replication health before relying on replicas. Synchronous replication could reduce the risk of losing acknowledged commits, but it can increase latency and make writes depend on standby availability. Failover requires a tested process to prevent two writable primaries.

Sharding could distribute customers or accounts by a stable customer/account key as data grows. Transfers between shards would require coordination across both sides of the transfer, making atomic money movement more complex. I did not implement sharding or cloud deployment.
