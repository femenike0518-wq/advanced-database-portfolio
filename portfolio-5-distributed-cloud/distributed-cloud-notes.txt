# SwiftBank Distributed and Cloud Database Notes

## Case study
SwiftBank is a fictional banking system that stores customers, accounts, balances and transactions. PostgreSQL is the authoritative system for relational data and money movement.

## Replication practical
I inspected PostgreSQL 18.6 replication settings on the primary and recorded `wal_level = replica`, `max_wal_senders = 10` and `hot_standby = on`. I then created a separate local physical standby on port 5433 using `pg_basebackup`. The primary's `pg_stat_replication` showed one client in `streaming` state with `sync_state = async`. A marker written to an isolated demo table on the primary appeared on the standby. A write attempt on the standby was rejected with SQLSTATE `25006`. Removing an accidental extra marker on the primary was also reflected on the standby.

This confirms that local asynchronous streaming replication was active during the practical. It does not show failover, production availability, sustained lag behavior or a cloud deployment. I did not alter SwiftBank's customer, account or transaction tables as part of the replication check.

## Sharding
If SwiftBank grew beyond one server's capacity, customer or account identifiers could be considered as shard keys. A transfer between accounts on different shards would need coordinated debits and credits; partial completion could create incorrect balances. This makes cross-shard transaction handling a major design concern.

## Consistency and availability
Banking balances require correct transaction processing. Asynchronous replicas can be stale while WAL changes are in transit, so reads that need the latest balance should use the primary or a consistency-aware design. Synchronous replication can improve commit durability across nodes but may add latency or reduce write availability when a standby is unavailable. Any failover must avoid two writable primaries and be tested before production use.

## Cloud considerations
A managed cloud PostgreSQL service could provide backups, monitoring and managed replicas, but the service configuration, access controls, recovery objectives, data location and cost would need to be evaluated. No cloud service was configured in this practical.
