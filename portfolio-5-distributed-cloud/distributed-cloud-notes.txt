SwiftBank Distributed and Cloud Database Notes

Case study
SwiftBank is a fictional banking system that stores customers, accounts, balances and transactions. The industry standard for relational data and financial transactions is PostgreSQL.

Replication practical
I verified PostgreSQL 18.6 replication settings on the primary and recorded `wal_level = replica`, `max_wal_senders = 10` and `hot_standby = on`. I then created a separate local physical standby on port 5433 using `pg_basebackup`. The primary's `pg_stat_replication` showed one client in `streaming` state with `sync_state = async`. A marker written to an isolated demo table on the primary appeared on the standby. A write attempt on the standby was rejected with SQLSTATE `25006`. Removing an accidental extra marker on the primary was also reflected on the standby.

This demonstrates that during the practical, local asynchronous streaming replication was operational. Failover, production availability, persistent lag behavior and cloud deployment are not displayed. During the replication check, I didn't make any changes to SwiftBank's customer, account or transaction tables.

Sharding
Customer or account identifiers might be regarded as shard keys if SwiftBank expanded beyond the capacity of a single server. Coordinated debits and credits would be required for a transfer between accounts on separate shards; incomplete transactions could result in inaccurate balances. Cross-shard transaction handling becomes a significant design issue as a result.

Consistency and availability
Accurate transaction processing is necessary for banking balances. I would direct reads that require the most recent balance to the primary or employ a consistency-aware design because asynchronous replicas may become stale while WAL changes are being transmitted. When a standby is unavailable, synchronous replication may increase latency or decrease write availability, but it can also increase commit durability across nodes. Before using it in production, I would need a tried-and-true failover procedure that avoids two writable primaries.

Cloud considerations
Backups, monitoring and managed replicas could be offered by a managed cloud PostgreSQL service; however, it would be necessary to assess the service configuration, access controls, recovery goals, data location and cost. In this practical, no cloud service was set up.
