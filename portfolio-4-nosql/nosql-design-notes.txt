# SwiftBank NoSQL Design Notes

## Document structure

I use one `customers` collection in the `swiftbank_nosql` database. Each document contains one customer and an embedded `accounts` array. This structure is convenient when an application view needs one customer's account details at the same time.

The customer names, emails, account numbers, account types and balances match the repeatable seed in Portfolio 1. The balance values are stored as BSON `Decimal128`. MongoDB describes Decimal128 as decimal-based and intended for monetary, tax and scientific data; this avoids the approximate binary representation used by `double` for many decimal fractions. PostgreSQL remains authoritative for account balances.

## Validation and indexes

The `customers` collection has a JSON Schema validator. It requires the customer ID, name, email, accounts and recent-transactions fields; account types are limited to `savings` and `current`; balances must be Decimal128 values; and recent transactions include a valid status and direction. Two unique indexes prevent duplicate `customer_id` and `email` values. My negative test attempts an unsupported account type, which the validator rejects.

The `recent_transactions` array is bounded to five items and contains the P1 seed transactions for the three MongoDB accounts. I preserve the failed withdrawal with `status: "failed"`, so it is distinguishable from completed money movement. Transfers also record direction and the counterparty account number. If a banking application needs a full transaction history, referencing a separate transaction collection avoids unbounded customer documents and supports querying transactions independently.

## Query and explain observations

I use an embedded-account query to find customers with savings accounts and an aggregation to count accounts and total balances by account type. The email lookup is covered by a unique index, and `explain("executionStats")` shows the selected plan and execution statistics. The collection has only three documents, so the plan demonstrates index use but does not prove a useful real-world speedup.

## Suitability and limitations

Embedding account details is convenient for reading a customer's account overview. It also duplicates balances from the relational database, which can become stale if updates are not synchronized. The PostgreSQL tables remain the source of truth for money movement because a transfer requires the debit, credit and ledger write to succeed atomically; this MongoDB exercise does not implement that workflow. The 1,000.00 transfers between SWB100002 and SWB100003 net to zero, so the embedded balances remain 80,000.00 and 30,000.00, matching the final P1 balances; SWB100001 remains at 50,000.00.

I did not use a key-value database because the portfolio focuses on a structured customer document rather than direct key access or caching. A wide-column database is more suitable for large distributed write and analytical workloads, while a graph database is useful when traversing relationships is central. Those needs are outside this small SwiftBank demonstration.
